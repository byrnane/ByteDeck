## Общее устройство

Теперь ByteDeck использует **renderer с фиксированными шаблонами экранов**.

Рантайм больше не считает `config/ui/screens/*.json` активным источником layout-структуры. Геометрия экранов задаётся кодом через жёсткий app shell и небольшой набор screen renderer'ов. Темы отвечают только за оформление.

Общая модель такая:

```text
screen state + bindings + theme -> fixed screen renderer -> SDL draw calls
```

## Основные слои

### `src/platform`

Отвечает за:

- вычисление рабочих путей
- загрузку пользовательских настроек
- загрузку переводов
- чтение статуса времени и батареи
- запись runtime-логов

### `src/data`

Отвечает за:

- нормализованные модели библиотеки
- сериализацию кеша библиотеки

Основные сущности:

- `GameItem`
- `AppItem`
- `Collection`
- `SystemEntry`
- `LibraryData`

### `src/core`

Отвечает за:

- сканирование ROM-каталогов
- парсинг `gamelist.xml`
- объединение метаданных и реальных файлов
- создание fallback-элементов
- сканирование приложений и коллекций
- сохранение нормализованного кеша

### `src/ui`

Отвечает за:

- перевод SDL-ввода в действия навигации
- локальную логику экранов
- загрузку темы и резолв theme-значений
- загрузку шрифтов и изображений
- рендер фиксированного shell и шаблонов экранов через SDL

Ключевые части:

- `FixedUiRenderer`
- `ThemeManager`
- `ThemeFontRenderer`
- классы экранов в `src/ui/screens/`

### `src/launch`

Отвечает за:

- единый интерфейс запуска игр и приложений
- соответствие систем ByteDeck и штатных TrimUI-скриптов
- отложенный handoff после полного завершения SDL на устройстве

### `src/app`

Отвечает за:

- инициализацию подсистем
- загрузку библиотеки
- создание SDL-окна и renderer'а
- управление стеком экранов и theme runtime
- сборку shell bindings
- координацию delayed handoff в эмулятор

## Контракт UI runtime

## App Shell

У всех экранов один и тот же shell:

- header сверху
- footer снизу
- content viewport по центру

Этот shell сначала рисует `FixedUiRenderer`, а уже потом поверх него рисуется экранный шаблон.

Header содержит:

- бренд
- текущий путь или контекст
- время
- батарею

Footer содержит:

- контекстные действия
- короткую подсказку

## Фиксированные шаблоны экранов

Первая версия fixed renderer поддерживает:

- `main_menu`
- `games`
- `game_browser`
- `apps`
- `settings`
- `placeholder`

У каждого экрана фиксированная композиция. Тема может менять цвета, шрифты, отступы, рамки, иконки и фоновые изображения, но не может перестраивать саму структуру экрана.

## Логика экранов

Экран остаётся code-first. Он по-прежнему отвечает за:

- навигацию
- состояние выбора
- drill-in состояние
- запросы на запуск
- переведённые строки
- подготовку bindings

Каждый экран отдаёт:

- `screen_id()`
- `build_bindings()`
- `window_title()`

Bindings больше не кормят универсальное layout-дерево. Теперь они кормят конкретный renderer для заранее известного шаблона экрана.

## Модель тем

Темы лежат здесь:

```text
themes/<theme-id>/
```

Точка входа:

```text
themes/<theme-id>/theme.json
```

Пути к assets всегда считаются относительными к папке темы.

Активная схема темы ориентирована на presentation layer. Она управляет:

- цветовыми токенами
- spacing-токенами
- шрифтами
- typography roles
- стилями shell
- общими стилями компонентов
- стилями отдельных экранов
- system icons

Стандартная тема сейчас использует такую структуру:

```text
tokens
fonts
typography
system_icons
shell
components
screens
```

## HTML-референс для авторинга

Визуальный контракт нового UI лежит здесь:

```text
ui_reference/index.html
ui_reference/screens/*.html
```

Эти файлы не используются в рантайме. Они нужны, чтобы:

- зафиксировать целевую композицию экранов
- показать, что зашито в renderer
- показать, что должно настраиваться через тему
- дать простой JavaScript-mock состояний интерфейса

Классы в HTML-референсе разделены на два namespace:

- `bd-builtin-*` для структурных частей, которые принадлежат renderer'у
- `bd-theme-*` для presentation-частей, которые должны выражаться через `theme.json`

## Legacy layout-файлы

Старые файлы в:

```text
config/ui/screens/
```

сейчас хранятся только как reference во время перехода. Они больше не участвуют в активном runtime path.

Старые `UiRenderer` и `LayoutRegistry` тоже оставлены только как reference-код и больше не собираются в основное приложение.

## Текст и изображения

### Текст

У ByteDeck два пути рендера текста:

1. theme fonts из TTF/OTF
2. встроенный bitmap fallback

За счёт этого интерфейс остаётся настраиваемым через темы, но не ломается, если кастомный шрифт не загрузился.

### Изображения

Renderer поддерживает:

- theme assets
- system icons
- preview-изображения
- placeholder-рендер, если картинка не найдена

Изображения кэшируются внутри renderer'а и рисуются как простые прямоугольные области.

## Runtime flow

Запуск:

1. `main.cpp` создаёт `Application`
2. `Application::initialize()` находит пути и включает логирование
3. из пользовательских настроек выбираются активная тема и язык
4. `ThemeManager` загружает активную тему
5. `TranslationCatalog` загружает переводы
6. `LibraryScanner` строит `LibraryData`
7. кеш записывается в cache root
8. инициализируются SDL-окно, renderer и ввод
9. `FixedUiRenderer` рисует shell и активный экранный шаблон

Запуск игры:

1. экран запрашивает запуск
2. `LaunchService` находит штатный launch script
3. на устройстве `Application` сначала завершает SDL loop
4. только после shutdown ByteDeck передаёт управление штатному скрипту

Такой отложенный handoff нужен, чтобы RetroArch-обёртки на устройстве корректно поднимали видеоинициализацию.
